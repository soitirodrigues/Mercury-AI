## 2. Architecture Before

- Sessao pre-F2:

## 3. Actual Session Flow

Fluxo canonico pre-F2 (wall + pipeline):

```
wall datetime.now(timezone.utc)  -> M5Clock._next_boundary/ceil_m5 -> M5OperationalRunner.run_cycle(target_candle=floor_m5)
  universe 39 (ALL_SYMBOLS)
  -> AnalysisPipeline.analyze por symbol -> provider (Yahoo) -> AnalysisResult
  -> rank_records / FreshnessGate / Top3

MercuryScanner.scan() (PATH alternativo legacy)
  config OPERATIONAL_PROFILE active=Demo broker=XP
  -> AssetRegistry.get_assets_for_broker -> XP.json 39
  -> filter enabled/profile -> symbols 39
  -> AnalysisPipeline.analyze por symbol
```

Fontes temporais:
- Live wall: `datetime.now(timezone.utc)` em `m5_operational/*`, `m5_incremental/*`, `operations/m5_sprint6*`
- Deterministic (analise): `DeterministicClock.utcnow()` em `core/analysis_pipeline.py`, `analysis/session_engine.py`, `analysis/*`, `core/*`, `models/*`
- Replay: `HistoricalReplayEngine.run_replay` → `DeterministicClock.set_time(candle) / restore()`
- Legado implicito: `MarketSessions` (pre-F2) usava `datetime.utcnow()` naive (assume UTC)

Dia da semana / mercado aberto: determinacao fragmentada — `MarketSessions.get_current_session()` decide por `hour` apenas (qual sessao Sydney..NewYork), nao por `weekday`; `YahooFinanceProvider` decide por `df.empty/<20` (falta de dados), nao por calendario.

Elegibilidade do ativo: pre-F2 nao existia distincao FOREX vs CRYPTO para decidir se o ativo pode ser analisado; filtering era apenas por `enabled/profile/XP.json`.

## 5. Forex Session Contract

- Regra operacional minima (Weekend UTC):
  ```
  FOREX -> eligible_for_live_analysis = (weekday UTC < 5)
         -> False em Sabado (5) e Domingo (6) UTC
         -> True em Seg-Sex
  STOCK/COMMODITY (compatibilidade, nao operacionais F1) -> mesma regra Forex
  ```
- Implementacao: `MarketSessions.is_market_eligible(market, now)` + `is_symbol_eligible(symbol, now)` + `_is_weekend_utc()`:
  - Usa `_utc_weekday(now)` — se `now` None, observa `DeterministicClock.utcnow()` (UTC), senao UTC explicado.
  - `CRYPTO/CRIPTO` early-return True (24/7), qualquer outro mercado aplica weekend.
  - `is_symbol_eligible` resolve market via `universe.get_asset(symbol).market` (fonte canonica), fallback por lista.
- Consumo: `MercuryScanner.scan()` e `M5OperationalRunner.run_cycle()` chamam `MarketSessions.is_market_eligible` por ativo antes de pipeline/worker. Feriados fora de escopo (secao FASE 4 — nao criados).

## 6. Crypto Session Contract

- Regra:
  ```
  CRYPTO -> eligible_for_live_analysis = True sempre (24/7), inclusive Sab/Dom
  ```
- Implementacao: mesmo `is_market_eligible` — ramo `m in (CRYPTO, CRIPTO) -> return True` sem checar weekday.
- Verificado explicitamente para BTC/USD, LTC-USD, LINK-USD, XPL-USD (F1) em Sab/Dom -> True; tambem semana -> True.
- Transicao domingo->segunda: mantem True (sem mudanca).

## 8. Provider Availability vs Session Eligibility

- Contrato F2 explicito:
  - `SESSION ELIGIBILITY` (regra `MarketSessions`) decide *se* o ativo deve ser tentado em live.
  - `PROVIDER DATA AVAILABILITY` (Yahoo `df.empty/<20` -> `DATA_PROVIDER_UNAVAILABLE`) decide se ha dados.
- Matriz relevante:
  - Yahoo retorna dados para Forex no weekend + Sessao CLOSED -> **Mercury marca como NOT ELIGIBLE e nao chama provider** (gate prevalece). Comportamento anterior seria analisar mesmo no weekend; F2 corrige.
  - Crypto OPEN + provider sem dados (ex: Yahoo vazio) -> continua `DATA_PROVIDER_UNAVAILABLE` (problema de dados, nao `MARKET_CLOSED`), sem mascaramento.
- Nao houve alteracao de provider; `YahooFinanceProvider`, `MarketDataService`, `HistoricalReplayProvider` intactos.

## 17. Architectural Risks

- Gate unico por `MarketSessions` (nao duplicado) — risco de drift mitigado (fonte canonica `universe.market`).
- Replay vs live: gate desacoplado por `is_frozen()` é correto para `HistoricalReplayEngine`, mas qualquer live real usando `DeterministicClock` frozen por outro motivo (ex: teste manual) tambem bypassa — comportamento desejado (argumento claro: frozen = deterministico). Risco residual baixo.
- Timezone: explicitamente UTC via `DeterministicClock`/ `datetime.now(timezone.utc)`; `MarketSessions` migrou para DeterministicClock (wording меняетo pode afetar consumidores legados que dependiam de utcnow naive — nao ha consumidores).
- Concurrency: ambos gates sao por call (`MarketSessions()` instanciado por scan/cycle), sem estado compartilhado; nenhuma corrida com `DeterministicClock` thread-local.
- Nao ha risco de `data/` gitignored: universo 39 intacto em `universe.py` versionado.
