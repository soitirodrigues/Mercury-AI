   regra 4 → WAIT)."

  1. ProbabilityEngine.analyze() calcula institutional_strength via coeficientes
     derivados dos pesos configurados (weight_trend/weight_structure/

  4. DecisionResolverEngine.resolve() regra 4: opportunity_grade == "D" → WAIT.
  5. Resultado: o sistema NUNCA produz BUY/SELL. Nenhum trade pode ser gerado.
     Toda análise termina em WAIT, independentemente da força do sinal.

Impacto: bloqueador operacional total de geração de trades. Confirmado por:
  - fórmula probe (seção 10): máximo alcançável 48.5 → grade D;

 3. ANÁLISE MATEMÁTICA DO BUG (POR QUE MÁXIMO = 48.5)
================================================================================
Com os pesos padrão de MercuryDecisionEngine:
    weights = {"trend": 0.4, "structure": 0.3, "liquidity": 0.2, "volatility": 0.1}

Coeficientes bugados:
    trend_structure_sum      = 0.4 + 0.3 = 0.7
    liquidity_volatility_sum = 0.2 + 0.1 = 0.3
    total_weight             = 0.7 + 0.3 = 1.0
    confluence_coef  = 0.7 / 1.0 * 0.50 = 0.35
    confidence_coef  = 0.3 / 1.0 * 0.35 = 0.105
    evidence_coef    = 0.15
    SOMA DOS COEFICIENTES = 0.35 + 0.105 + 0.15 = 0.605  ← NÃO é 1.0!
    (o comentário do código prometia soma = 1.0, mas a multiplicação por
     0.50/0.35 DEPOIS da normalização por total_weight esmaga a soma.)

Institutional strength MÁXIMO (confluence=100, confidence=100, evidence_bonus=20,
risco=0):
    = 100*0.35 + 100*0.105 + 20*0.15
    = 35.0 + 10.5 + 3.0
    = 48.5  <  50  →  grade "D" SEMPRE  →  regra 4  →  WAIT SEMPRE
    ✓ Confirmado: este é exatamente o valor 48.5 reportado na auditoria.

O defeito é a MULTIPLICAÇÃO DUPLA: (weights/total) * {0.50 ou 0.35}. A
normalização por total_weight já entrega proporções que somam 1.0; multiplicar
por 0.50/0.35 depois reduz os coeficientes de confluence/confidence pela metade
e por 2/3, respectivamente, sem que o evidence_coef (0.15, fixo) compense.
