5. CAUSA RAIZ
--------------------------------------------------------------------------------
HistoricalReplayEngine.run_replay congelava DeterministicClock via
set_time(current_time) a cada candle do loop e NUNCA restaurava o estado ao
final. Como reset() não era chamado em nenhum lugar da produção, o relógio
permanecia preso no último timestamp histórico após o retorno de run_replay.

Localização: mercury_ai/analysis/historical_replay_engine.py
  - loop: for i in range(start_idx, len(full_df) - n_candles)
  - set_time dentro do loop (era linha 130)
  - sem reset/restauração após o loop

DeterministicClock: mercury_ai/utils/deterministic_clock.py
  - estado global de classe _current_time
  - reset() existia mas NUNCA era chamado em produção

6. CONTRATO ESPERADO
--------------------------------------------------------------------------------
Contrato derivado do CÓDIGO ATUAL (não inventado):

DURANTE replay:
  DeterministicClock = timestamp histórico do candle atual
  (set_time por candle — comportamento atual, CORRETO; preservado)

DEPOIS do replay:
  DeterministicClock NÃO pode permanecer no passado.
  O estado temporal anterior deve ser RESTAURADO (snapshot/restore)
  — o mecanismo mais correto: preserva exatamente o estado pré-existente,
  inclusive se um caller tiver congelado o clock deliberadamente antes do
  replay (ex.: replay aninhado), em vez de resetar cegamente para None.

O projeto já possuía reset() (volta ao relógio real), mas snapshot/restore é
estritamente mais correto para ISOLAMENTO: restaura o estado exato anterior.

PROPRIEDADES:
- During replay: clock congelado no histórico (inalterado).
- After replay: clock restaurado ao estado anterior (finally).

  nunca é tocado (set_time não é chamado) -> sem necessidade de restore.
- Thread-safety: snapshot/restore usam o lock de classe existente.

14. THREAD / GLOBAL STATE (seção 10 da missão)
--------------------------------------------------------------------------------
DeterministicClock é:
  - GLOBAL / CLASS-LEVEL: _current_time e _lock são atributos de classe,
    compartilhados por todas as threads do processo.
  - NÃO é thread-local, NÃO é contexto, NÃO é stack de timestamps.

Sincronização: _lock (threading.Lock) de classe garante atomicidade de
set_time / utcnow / snapshot / restore individuais.

CALLERS DE run_replay (verificado no código):
  - run_deterministic_replay_scenarios.py : SEQUENCIAL (loop for)
  - run_institutional_replay.py            : SEQUENCIAL (loop for)
  - ReplayBatchProcessor.run_batch         : PARALELO (ThreadPoolExecutor,
    max_workers configurável, default 4) -> run_replay em threads por símbolo.

RISCO DE CONCORRÊNCIA (pré-existente, FORA do escopo desta correção):
  Se dois replays rodarem em threads paralelas, o _current_time de classe é
  compartilhado: os set_time de cada thread podem se intercalar e o timestamp
  "atual" visto por cada candle pode pertencer à OUTRA thread durante o replay.
  A correção B4-C1 (snapshot/restore) NÃO piora este cenário: cada thread
  restaura o estado capturado ao final. O risco de corrida DURANTE o replay é
  anterior a esta correção e pertence ao desenho global do DeterministicClock.

REGISTRADO COMO PENDÊNCIA (não expandir escopo):
  - ReplayBatchProcessor em paralelo + DeterministicClock de classe = corrida
    de timestamps DURANTE replay. Endereçar em bloco futuro (ex.: clock
    thread-local, ou lock de replay abrangendo o loop inteiro).
  - Para o contrato SEQUENCIAL (uso primário de produção), a correção é
    suficiente e correta.
