## Critério 1: audit_id determinístico
- **Evidência**: audit_id = "X" usado consistentemente em todas as execuções A e B
- **Origem**: ReplayStorage.save() usa audit_id diretamente no nome do arquivo
- **Resultado**: ✅ PASS - audit_id mantém-se determinístico em todas as operações

## Critério 2: replay_id separa execuções
- **Evidência**: Dois replay_ids distintos (rA = 11e592..., rB = 0e4fed4...) criam arquivos distintos:
  - X_{rA}_A.json e X_{rB}_B.json
- **Origem**: compute_replay_id_from_snapshot() usa SHA-256(asset|timeframe|timestamp|session_id|audit_id)
- **Resultado**: ✅ PASS - replay_id separa execuções de forma determinística

## Critério 3: run_id separa execuções
- **Evidência**: run_id A/B cria sufixos _A e _B no nome do arquivo
- **Origem**: ReplayStorage.save() usa run_suffix = f"_{safe_run_id}" quando run_id fornecido
- **Resultado**: ✅ PASS - run_id separa execuções; diferentes run_ids produzem arquivos diferentes

## Critério 4: A não sobrescreve B
- **Evidência**: Save idêntico (mismo run_id) lança ValueError: "duplicate replay identity detected"; run_ids diferentes permitem co-existência
- **Origem**: ReplayStorage.save() verifica _existing_file_matches() antes de escrever
- **Resultado**: ✅ PASS - A não sobrescreve B; duplicate exato é detectado e rejeitado

## Critério 5: duplicate exato detectado
- **Evidência**: Segundo save() com parâmetros idênticos ao primeiro lança ValueError; save com run_id diferente permite co-existência
- **Origem**: ReplayStorage.save() - _existing_file_matches() compara dicionários completos de dados
- **Resultado**: ✅ PASS - duplicate exato é detectado; "último arquivo" não é considerado correto

## Critério 6: snapshot/métricas incompatíveis não são pareados
- **Evidência**: Fix no institutional_analytics_engine.py _load_data(): `if replay_id:` → `metrics = replay_metrics.get(replay_id)`; `elif audit_id:` → `metrics = replay_metrics.get(audit_id)` — fallback por audit_id SOMENTE quando snapshot NÃO tem replay_id
- **Resultado**: ✅ PASS - snapshots com replay_id não são arbitrariamente pareados com métricas via audit_id; snapshots sem replay_id usam fallback controlado

## Critério 7: legacy ambiguity não produz associação arbitrária
- **Evidência LearningEngine**: `id_to_context[audit_id]` não usa mais "last-wins"; agora usa `audit_to_contexts[audit_id].append(snap)`; pareamento só ocorre quando audit_id mapeia ao único snapshot (len == 1), caso contrário skip (AMBIGUOUS)
- **Evidência InstitutionalMemoryEngine**: `record_outcome(audit_id, outcome, replay_id="")` agora filtra por replay_id quando fornecido; sem replay_id, comportamento legacy mantido mas documentado
- **Resultado**: ✅ PASS - legado ambiguity não produz associação arbitrária; detecção de ambiguidade explícita quando múltiplos snapshots compartilham audit_id

## Critério 8: Analytics não mistura
- **Evidência**: Fix no _load_data() garante pareamento rigoroso por replay_id quando presente; fallback audit_id só quando snapshot sem replay_id
- **Resultado**: ✅ PASS - Analytics não mistura A e B; pareamento segue identidade de replay

## Critério 8: Learning não mistura
- **Evidência**: LearningEngine agora: se métrica tem replay_id → ctx = id_to_context.get(m["replay_id"]); se sem replay_id → audit_to_contexts.get(audit_id, []) → len(matches) == 1 → ctx = matches[0]; len != 1 → ctx stays None (skip)
- **Resultado**: ✅ PASS - Learning não mistura A e B; associação arbitrária eliminada

## Critério 9: Memory não mistura
- **Evidência**: InstitutionalMemoryEngine.record_outcome(audit_id, outcome, replay_id="") agora filtra: entry['audit_id'] == audit_id AND (not replay_id OR entry.get('replay_id', '') == replay_id)
- **Resultado**: ✅ PASS - Memory não mistura A e B quando replay_id fornecido; legacy (sem replay_id) mantido mas documentado como limitação

## Critério 10: Concorrência com MESMO audit_id é segura
- **Evidência**: ReplayStorage usa threading.Lock para proteger operações de save; testes de concorrência mostram ambos completes, dois registros permanecem, conteúdos A/B intactos
- **Resultado**: ✅ PASS - concorrência com mesmo audit_id é segura graças ao lock

## Critério 11: restart preserva A/B
- **Evidência**: Simulação de restart (verificação de arquivos persistentes + novo save C) — A e B preservados; C adicionado sem afetar A/B; arquivos atômicos via atomic_json_write garantem integridade
- **Resultado**: ✅ PASS - restart preserva A/B

## Critério 12: Atomic recovery demonstrada ou limitada
- **Evidência**: Estrutura do atomic_json_write garante: old file XOR new file, nunca parcial/partial; tempfile + fsync + os.replace + retry loop with exponential backoff; testado: simulação de crash antes de json.dump lança RuntimeError e arquivo não criado
- **NOT PROVEN**: Crash injection real em nível de SO (kill process mid-write) não realizada; per requirement do spec, declarado NOT PROVEN quando injecção real não possível
- **Resultado**: ✅ DEMONSTRADO (estructural) / ❌ NOT PROVEN (crash real)
