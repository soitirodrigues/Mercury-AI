- Evidence: System correctly produces different replay_ids when any field changes, even with same audit_id

**Evidence**: 
- Formula: `SHA-256(asset|timeframe|timestamp|session_id|audit_id)`
- Test: Same audit_id, different timeframe → different replay_id (verified)
- Test: Same audit_id, different session_id → different replay_id (verified)
- Test: Same audit_id, different timestamp → different replay_id (verified)
- Test: Same audit_id, different asset → different replay_id (verified)
- No single-field manipulation can force a collision — all fields contribute to the hash

### 13. TEST C4-13: atomic write/recovery

**Objective**: Prove that atomic writes are recoverable and no data is lost.

**Implementation**:
- Executed ReplayStorage.save() multiple times
- Simulated crash scenarios (process termination during write)
- Verified that after recovery, all saved metrics are intact or the file is in clean state

**Result**: ✅ PASS
- `atomic_json_write` uses tempfile + os.replace pattern
- `os.replace()` is atomic at filesystem level
- If crash occurs during write: temp file left behind, original file intact
- If crash occurs after replace: new file in place, no corruption
- Evidence: Recovery tests show all-or-nothing — either old file or new file, never corrupt

**Evidence**: 
- `atomic_json_write` pattern:
  - `tempfile.mkstemp(suffix=".tmp", prefix=".snap_", dir=str(self.base_path))`
  - Write data to fd, flush, fsync
  - `os.replace(tmp_path, filepath)` — atomic on POSIX/Windows
- Crash before `os.replace`: temp file orphaned, original file intact
- Crash after `os.replace`: new file in place, original overwritten atomically
- Test: Multiple save() calls, process kill at various points, recovery always successful
- No partially-written or corrupt files observed
