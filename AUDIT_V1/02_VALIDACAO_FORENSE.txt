6. ESCALAS
--------------------------------------------------------------------------------
ACHADO DO INVENTÁRIO: "escala de confiança inconsistente (0-100 vs 0-1)"
CLASSIFICAÇÃO DO ACHADO ESPECÍFICO: REFUTADO (ver explicação)
CLASSIFICAÇÃO DA SITUAÇÃO GERAL: PARCIALMENTE CONFIRMADO (mix de escalas documentado)

Evidência:
- `ConfidenceEngine.calculate()` produz escala 0-100 internamente
  (score = 100*(0.25*q + 0.45*c + 0.30*m), clamp 0-100).
- PORÉM `DecisionResultBuilder` (decision_result_builder.py:114) faz
  `confidence = calibrated_confidence / 100.0` — DESIGN NOTE explícita:
  "confidence é armazenado em escala 0-1 (não 0-100) por compatibilidade
  histórica com todos os consumidores UI que usam decision.confidence*100".
- `confidence_calibration_auditor.py` lê `data['decision_result']['confidence']`
  e usa bins `np.linspace(0,1,6)` — CONSISTENTE porque o valor armazenado é 0-1.
- O achado "escala mismatch que quebra o auditor" é REFUTADO: o auditor lê a
  escala 0-1 armazenada, não a 0-100 interna do ConfidenceEngine.
- RESIDUAL (PARCIALMENTE CONFIRMADO): `DecisionResult` MISTURA escalas —
  confidence=0-1 enquanto score/quality/clarity/risk_score e as probabilidades
  são 0-100. É um design documentado, mas um risco real de confusão para
  consumidores que esqueçam de multiplicar confidence*100.
- Confirmação por runtime: probe produziu confidence=0.699 (0-1) e
  buy/sell/wait=40/0/60 (0-100, soma 100). Escalas coerentes com o design.

7. OHLCV (Case das colunas)
--------------------------------------------------------------------------------
ACHADO DO INVENTÁRIO: "inconsistência de case das colunas OHLCV
  ('Close' vs 'close') -> risco de KeyError entre módulos"
CLASSIFICAÇÃO: REFUTADO como bug vivo no fluxo principal; PARCIALMENTE
  CONFIRMADO como fragilidade de design (dependência de normalização central)

Contrato real (verificado no código):
1. Adapters (providers/data_adapters.py YahooAdapter etc.) produzem MINÚSCULO
   (rename "Open"->"open", "High"->"high", "Low"->"low", "Close"->"close",
   "Volume"->"volume").
2. `DataNormalizer.normalize()` (data/data_normalizer.py) converte tudo para
   minúsculo, mapeia sinônimos, preenche ausentes e **DUPLICA OS DOIS PADRÕES**
   (adiciona "Open/High/Low/Close/Volume" ao lado do minúsculo). Saída = AMBOS.
3. `MarketDataService.get_data()` (data/market_data.py) SEMPRE chama
   `_normalize_dataframe` (nos dois ramos: provider_manager e providers antigos)
   -> retorna AMBOS os cases.
4. Caminho principal: scanner -> pipeline -> `market_service.get_data()` (linha 171)
   -> df com AMBOS os cases -> TODOS os engines funcionam (Capitalized e lowercase).
5. Caminho replay: parquet `data/replay/EURUSD=X/data.parquet` tem colunas
   MINÚSCULAS (verificado: close/high/low/open/volume, 6077 linhas).
   `historical_replay_engine.py:90-92` (volume/close/open lowercase) funciona com
   esse parquet. O pipeline do replay usa MarketDataService -> normaliza -> OK.
6. Engines que se auto-normalizam (swing_engine.py:58,176;
   market_structure_intelligence_engine.py:93) funcionam com qualquer case.
   Engines que NÃO se auto-normalizam (historical_replay_engine:90;
   smart_money/market_structure_engine.py:23-24) dependem do caller normalizado.

Verdict: a inconsistência é real (convenções diferentes entre engines), mas é
NEUTRALIZADA pelo DataNormalizer no fluxo canônico. KeyError só ocorreria se um
caller burlar MarketDataService/DataNormalizer (adapter direto, df manual em
scripts/tests) ou se o parquet de replay fosse Capitalizado (hoje é minúsculo).
=> REFUTADO como bug vivo; CONFIRMADO como fragilidade de design (acoplamento
   à normalização central; engines lowercase sem auto-defesa).

   - REJEITA dados com gaps temporais >15min ("Temporal gaps detected") ->
     parquet EURUSD=X (5min com gaps de fim de semana) -> WAIT
     (audit_id='DATA_QUALITY_FAIL'). Dados contínuos passam.
   - Este gate é STRICT: dados 5min de semanas com fim de semana são rejeitados.

E) Efeitos colaterais do probe (runtime_report + 2 snapshots EURUSD_X)
   foram identificados e REMOVIDOS (investigação não altera o repo).

20. VEREDITO
--------------------------------------------------------------------------------
PERGUNTA: "Podemos afirmar, com evidência suficiente, que o Mercury AI V1 está
funcionando corretamente?"

RESPOSTA: NÃO, com a configuração e o estado atuais NÃO é possível afirmar que o
Mercury AI V1 está funcionando corretamente DE PONTA A PONTA.

Fundamentação com evidência:
1. O NÚCLEO do motor de decisão demonstra funcionamento correto quando alimentado
   com dados válidos: probe executou o pipeline completo (18.5s) e produziu
   decisão coerente com escalas válidas, sem NaN, sem None, sem valores
   impossíveis, confiança 0-1 e probabilidades somando 100.
2. PORÉM, o sistema como entregue NÃO executa o fluxo de produção: o entry
   point oficial escaneia zero ativos (data/brokers vazia), o segundo entry
   point quebra (NameError), e as dependências não instalam (requirements
   corrompido). Ou seja: não há evidência de funcionamento correto do SISTEMA
   em uso real — há evidência de que o motor funciona isoladamente.
3. Existem fragilidades estruturais confirmadas que impedem afirmar corretude:
   fonte dupla de verdade de pesos, tabelas de mapeamento divergentes, engines
   documentados como oficiais fora do fluxo, e mascaramento parcial de erros
   (PIPELINE_ERROR vira WAIT na superfície).
4. Verdict parcial sobre o NÚCLEO: APROVADO COM RESSALVAS (núcleo executa e
   produz valores válidos; ressalvas de pesos, mapeamentos e gate de dados).
5. Verdict sobre o SISTEMA/PRODUTO: REPROVADO para "funcionando corretamente"
   — o runtime oficial não realiza análise, um entry point quebra e o ambiente
   não é reproduzível via requirements.

Recomendação (fora do escopo desta fase, que é investigação-only): antes de
qualquer operação real, corrigir requirements.txt, restaurar/reconfigurar
data/brokers, restaurar o entry performance_benchmarking, e unificar a fonte de
pesos/mapeamentos. Nenhuma dessas alterações foi feita nesta fase.
